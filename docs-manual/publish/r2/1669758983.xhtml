At a glance

Purpose

Install and configure the Analyzer Bridge so analyzers can deliver results into OpenELIS, and so OpenELIS can read the Bridge's analyzer type catalogue.

You'll end up with

A running Bridge whose health endpoint reports UP, and an OpenELIS instance whose Analyzers → Analyzer Types list is populated rather than empty.

Who does this

Lab IT or whoever runs the OpenELIS server. This is a server task, not a screen in OpenELIS. Access is set by user permissions and can be configured by your administrator.

Before you start

An x86-64 (amd64) host with Docker, the OpenELIS base URL, a password you will set for the Bridge, and the analyzers you intend to connect. A TLS keystore is optional: the Bridge generates its own certificate if you do not supply one.

Where

The Bridge host's shell. Nothing here is done from the OpenELIS interface.

What the Bridge is responsible for

The Bridge and OpenELIS split the work along a deliberate line, and most configuration mistakes come from putting something on the wrong side of it.

The Bridge owns

Analyzer profiles, durable analyzer connections, the listeners themselves, message parsing, control-result recognition, file watching, and delivery of one normalised result to OpenELIS.

OpenELIS owns

The lab-facing setup workflow, references to Bridge connections, lab units, local test catalogue bindings, verification and audit, activation intent, quality control, held results, and review.

A profile describes how one analyzer type communicates, and supplies the defaults used when a new connection of that type is created. A connection is one durable, saved instrument: it pins a profile revision and owns its own source binding. Every normalised result the Bridge delivers carries its connection ID, and OpenELIS looks the analyzer up by that ID rather than inferring identity from the analyzer's name.

Protocol versus transport

These are configured separately and are easy to conflate. Protocol is the shape of the message; transport is how it arrives.

Protocol

ASTM, HL7, CSV — the message format and syntax

Transport

TCP, MLLP, Serial, File, HTTP — how the message reaches the Bridge

The pairing matters when you read a connection's settings: an HL7 connection over MLLP and an ASTM connection over TCP are both "a socket on a port", but they parse nothing alike, and the profile is what decides the parsing. One combination is explicitly rejected: HL7 in TCP client mode for inbound results is not supported. Inbound HL7 must be a server connection that the analyzer connects to.

That message is correct on a fresh install: the listener is bound, but no saved analyzer is attached to it yet.

A published port answering does not mean anything is listening. Docker's port forwarder accepts connections on a published host port whether or not the container has bound it, so a successful telnet or nc proves nothing. Check inside the container with docker exec <container> netstat -ltn, or read the health endpoint.

Step 2 — TLS: let the Bridge generate its certificate, or supply your own

The default active profile is prod, set inside the image, so you do not need to select it. On first start, if no keystore is supplied, the Bridge generates its own key pair and serves HTTPS with a self-signed certificate (subject CN=openelis-analyzer-bridge). It stores the identity under /data/openelis-analyzer-bridge/identity/, so keep that volume across restarts or the Bridge will present a new certificate.

If your site requires its own certificate, supply a PKCS12 keystore; it is used as given:

yamlwide760- -Dserver.ssl.keyStoreType=PKCS12 -Dserver.ssl.keyStorePath=/app/bridge-keystore.p12 -Dserver.ssl.keyStorePassword=CHANGE_ME volumes: - ./bridge-keystore.p12:/app/bridge-keystore.p12:ro]]>

Profile variable naming. The shipped docker-compose.yml selects the dev profile with SPRING_PROFILES_ACTIVE: dev, while the image's entrypoint reads a differently named SPRING_PROFILE (tracked as openelis-analyzer-bridge#80). For a production lab, remove the SPRING_PROFILES_ACTIVE: dev line so the image's default prod profile applies, and do not set SPRING_PROFILE as well: if both are set, SPRING_PROFILE wins.

Step 3 — Set the Bridge password

panel_c1

Set BRIDGE_AUTH_PASSWORD. OpenELIS cannot reach the Bridge without it. From 3.2.7 the Bridge's default password is empty, which means "pairing only": with no password set, no username and password is accepted, not even a blank one. OpenELIS at the time of writing authenticates to the Bridge with a username and password and cannot yet pair, so a Bridge without a password leaves the analyzer type list empty.

yamlwide760

The shipped default changeme is still refused. If you set it, the Bridge logs an error and exits with status 1 unless the profile is dev or test:

When a password is set, the startup log confirms it with bridge.security.password is accepted until this Bridge is paired with OpenELIS. A pre-hashed value is also accepted, in Spring's delegating form — {bcrypt}$2a$10$.... Changing the credential requires a restart.

This one password protects the management API that OpenELIS calls, so whatever you set here is what OpenELIS must be given in Step 5.

panel_c1

Do not pair the Bridge yet. Every unpaired Bridge logs a pairing code at each start, for example Bridge is not paired with OpenELIS. Enter this pairing code in OpenELIS to pair it: XXXX-XXXX-XXXX-XXXX-XXXX. Pairing by certificate replaces the password, and the first pairing ends password access. OpenELIS support for pairing is still in review (OpenELIS-Global-2#4657), so pairing a Bridge now would lock out an OpenELIS that still uses the password. Leave the code unused until your OpenELIS version supports pairing; this page will be updated when it does.

Step 4 — Configure Bridge → OpenELIS (the forward URI)

This is the direction results travel. It lives in configuration.yml, which the Bridge reads from the hard-coded path /app/configuration.yml — that mount path is required, not a convention. If the file is absent the Bridge starts anyway on its built-in defaults and logs Properties location [file:/app/configuration.yml] not resolvable, which is easy to miss.

yamlwide760 password: insecure-tls: false health-uri: https://openelis.example.org:8443/api/OpenELIS-Global/analyzer/health connect-timeout-seconds: 30 read-timeout-seconds: 30]]>

Give the base URI. The Bridge appends /fhir itself and posts the normalised result bundle there, for every protocol and transport — there is no per-protocol URI to configure. The username and password here are sent only while the Bridge is unpaired.

health-uri must be on the same host as uri. If it is not, the Bridge logs an ERROR at startup, and the health check goes green while deliveries are going nowhere. If you leave it unset, the httpforward health indicator reports UNKNOWN rather than failing, so an unset value looks like a working but unmonitored forward path.

Results are not lost while OpenELIS is down. Every received result is written to a durable outbox before any network call and retried — by default up to 150 attempts with backoff, sized to survive an overnight outage — until OpenELIS accepts it or it lands in the dead-message queue with its payload intact. Point bridge.outbox.db-path at a persistent volume: between receipt and delivery, that file is the only copy of the result.

Step 5 — Configure OpenELIS → Bridge (what populates the analyzer type list)

This is the direction people forget, and it is the one that makes Analyzers → Analyzer Types work. OpenELIS reads the Bridge's profile catalogue over the Bridge's authenticated management API. Without these three properties, OpenELIS has no catalogue to show, the analyzer type list is empty, and the wizard in Set up an analyzer cannot proceed.

Set them in the OpenELIS common.properties:

propertieswide760

Property

Must match

analyzer.bridge.url

The Bridge's published API port, with no trailing path. OpenELIS appends /api/profiles and the connection paths itself.

analyzer.bridge.username

bridge.security.username on the Bridge (default bridge).

analyzer.bridge.password

The BRIDGE_AUTH_PASSWORD you set in Step 3.

Use https://. The Bridge serves TLS on that port, so a plain HTTP request is answered with 400 Bad Request — This combination of host and port requires TLS. OpenELIS deliberately trusts any certificate on this hop, so the Bridge's generated self-signed certificate is fine and you do not need to import it into OpenELIS.

Neither credential may be blank: OpenELIS raises Analyzer Bridge username must be configured (or the password equivalent) rather than attempting an anonymous call, so a half-configured Bridge fails loudly rather than looking unreachable.

Confirm this direction before touching OpenELIS

Run the same request OpenELIS makes. This is the single most useful check in the whole installation:

bashwide760

A healthy response carries schemaVersion, a catalogFingerprint, a profiles array and an issues array (empty when every profile loaded). A stock 3.3.0 Bridge ships three profiles: Bruker FluoroCycler XT (FILE), Cepheid GeneXpert (ASTM Mode) (ASTM), and Thermo Fisher QuantStudio QS5/QS7 (FILE). If this call returns 200 and OpenELIS still shows an empty type list, the problem is in OpenELIS's properties, not the Bridge. If it returns 401 with the password you set, the password does not match; if it returns 401 for every password, check that BRIDGE_AUTH_PASSWORD actually reached the container (Step 3) and that the Bridge has not been paired.

Step 6 — Check health

bashwide760

Anonymously, /actuator/health returns only {"status":"UP"}. Component detail requires authentication: with the password, a healthy idle Bridge reports "status":"UP" with components diskSpace, filewatcher, httpforward, mllp, outbox, ping and serial. "mllp" saying "no active saved HL7 connections" is correct on a fresh install, not a fault.

Per-transport endpoints such as /actuator/health/mllp return 401 without credentials and 200 with them.

Tips

  • Work through the two directions separately. The forward URI failing and the management API failing look nothing alike: the first shows up as results queuing in the outbox, the second as an empty analyzer type list in OpenELIS.

  • Without a Bridge, the analyzer module looks present but cannot register an instrument. On an OpenELIS with no Bridge configured, Analyzers → Analyzer Types shows "Analyzer types could not be loaded — Check the Analyzer Bridge connection, then try again", and Add Analyzer cannot be completed because its Analyzer type field has nothing to offer.

  • Publish only the shared ports you use. If no analyzer will use HL7, leave MLLP_ENABLED off and do not publish 2575.

  • Preserve /data across restarts. The connection catalogue, profile catalogue, file-processing state, delivery outbox and the Bridge's generated identity all live there. On restart the Bridge restores active connections from their last successfully activated values — so a connection edited but never activated comes back as the older working version, which is intended behaviour and surprises people.

  • Deactivation is not instant. Closing a connection waits up to 30 seconds for deliveries in flight. A failed drain reports failure and keeps ownership; do not treat it as complete.

  • A restart does not recover a lost outbox. If the outbox database cannot be opened the Bridge renames it aside, logs the path at ERROR and starts a fresh one so the lab keeps working. That renamed file is incident evidence — preserve it and reconcile against OpenELIS.
