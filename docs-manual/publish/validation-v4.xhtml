This page documents the redesigned Validation page introduced in OpenELIS 3.2.2.0. If your site is on an earlier release, use Validate and release results instead, which describes the previous worklist with its Save / Retest checkboxes.

How-to · Validator

At a glance

PurposeWork through the results waiting for validation, decide each one, and release the ones that are ready.
You’ll end up withReleased results, which leave the queue — or results corrected, sent back for retesting, or left in the queue for a second look.
Who does thisValidators. Access is set by user permissions and can be configured by your administrator.
Before you startResults entered and saved on the Results page, so they carry the status Accepted by technician.
WhereMain menu → Validation → Routine.

Overview

The Validation page shows one queue per test unit. Above the queue, a row of filter chips counts the rows carrying each signal, and two lane tags count the whole queue as Clear or Needs review. Each row opens a review panel in place, showing the result in context — reference and critical ranges, method, analyzer, who entered it and when, QC, components, notes and history — with the release, correction and retest actions together at the bottom of the panel.

Reviewing happens inside the queue. There are no per-row Save and Retest checkboxes and no Save All Normal / Retest All Tests buttons; each result is decided in its own panel, or released in bulk with Release all clear.

Step 1 — Open the validation worklist

Open Main menu → Validation → Routine. The page opens with no test unit chosen, so the queue reads There are no records to display.

{{IMG:01-open-validation.png}}

The Validation page before a test unit is chosen.

Step 2 — Choose a test unit and read the queue

  1. Pick a unit from Select Test Unit — for example, Hematology. The results awaiting validation for that unit load.
  2. Read the header before the rows. The legend explains the red flag icon (Sample or Order is nonconforming or Test has been rejected); Release all clear sits at the right with the number of rows it would release; the filter chips below count the rows carrying each signal — All, Needs review, NCE, QC fail, Modified, Ack pending, Critical and Abnormal; and the two lane tags on the right count the queue as Clear and Needs review.
  3. Scan the rows. Each row shows Sample Info, Test Name, Normal Range, Result, U (k=2), Check before release and Past Notes. A result outside its normal range carries an amber bar and an Abnormal flag; a result inside its range carries a green bar and no flag. Where a row carries a signal you should look at before releasing it, that signal appears as a chip in Check before release, above the row’s Review link.

{{IMG:02-triage-queue.png}}

The Validation queue for one test unit, with the filter chips, the lane tags and one row per result.

Step 3 — Narrow the queue with a filter

Click a filter chip to show only the rows it counts — Abnormal, for example. The chip highlights and the row count at the foot of the table follows the filter. The Clear and Needs review tags keep counting the whole queue, not the filtered view, so they do not change as you filter. Click All to return to the full queue.

{{IMG:03-filter-abnormal.png}}

The Abnormal filter applied: five of the eight rows remain, while the lane tags still count all eight.

Step 4 — Open a result for review

Click Review → on a row, or the chevron at the left of the row. The review panel opens underneath it, headed by the lab number and patient, and shows:

  • Result with its units and flag, and the Reference range.
  • Critical range, Method, Analyzer, Entered by, Entered on and QC. Fields the laboratory has not captured read Not recorded.
  • Where the row carries signals, a Before releasing, check: line listing them.
  • For a test with more than one component, a Components table listing each component with its result, units, reference range and flag.

{{IMG:04-review-panel.png}}

The review panel for one result, including the Components table for a multi-component test.

Step 5 — Check the history before you decide

At the bottom of the panel, the REFERENCE block holds Notes, QC, Order info, History (this analysis) and Attachments. Expand History (this analysis) to see the entries for this analysis — when, the event (Created, Result, Status), the detail, and who recorded it. As the panel notes, patient trends live on the patient record and Westgard rules on the QC dashboard.

{{IMG:05-reference-history.png}}

History (this analysis) expanded, showing the result entry and the status change that put the result in this queue.

Step 6 — Add a validation note

Type in Validation note if the decision needs explaining, then set Visibility:

  • Internal keeps the note inside the laboratory.
  • Send with result puts the note on the patient report. This option is selected by default, and the panel says so beneath the buttons: This note will appear on the patient report.

The note is recorded against the validation step automatically — the panel shows Context: Validation (recorded automatically).

{{IMG:06-validation-note.png}}

A validation note typed into the panel, with Visibility set to Send with result.

Step 7 — Release the result

Click Validate & release. The result is released, the row leaves the queue, and the filter counts and lane tags drop to match. All components of a multi-component test leave together. On the Results page the released test then reads Results final.

{{IMG:07-after-release.png}}

The queue after a release: the released rows are gone and the counts have dropped.

Step 8 — Correct a result before releasing it

Click Modify result to correct a value without leaving the queue. The panel adds a New result field holding the current value, and relabels the note field Reason for modification with Visibility set to Internal. Save modification and Cancel replace the usual action buttons.

{{IMG:08-modify-result.png}}

Modify result open on a row, with the New result field and the reason for the change.

Enter the corrected value and the reason, then click Save modification. The row stays in the queue with the new value, gains a Modified chip in Check before release, and is counted by the Modified filter. The reason appears in the row’s Past Notes with its visibility and timestamp, and in the panel’s Notes section as a Result Note (Modification). The result still has to be released.

{{IMG:13-after-modify.png}}

After saving a modification: the corrected value, the Modified chip, and the reason carried into Past Notes.

Step 9 — Send a result back for retesting

Click Send for retest. The panel switches to a confirmation step: the note field becomes Note for the bench, Visibility switches to Internal, and a red Send for retest button appears beside Cancel with the explanation The result goes back to Results Entry and the pipeline restarts at level 1.

{{IMG:15-retest-filled.png}}

The retest confirmation step, with a note for the bench explaining why the result is going back.

Write the note for the bench, then click the red Send for retest to confirm. The row leaves the queue and the counts drop. On the Results page the test reappears for entry with the status Not accepted by biologist.

{{IMG:16-after-retest-confirmed.png}}

The queue after a confirmed retest: the row has gone back to Results Entry.

Reaching the queue another way

The same queue is used by the other entries under Validation. By Order asks for a lab number instead of a test unit and then shows the identical table, filter chips and lane tags, plus an Include auto-validated toggle that is off by default. By Range of Order Numbers and By Date ask for a starting lab number and a test date respectively.

{{IMG:11-by-order.png}}

By Order: the same queue reached by lab number, with the Include auto-validated toggle.

Tips

  • Neither releasing nor retesting produces a confirmation message. The row disappearing from the queue, and the counts dropping, is the confirmation.
  • Rejecting a result is configuration-dependent. Where it is turned off, the panel says so in place of the button: Result rejection is turned off for this laboratory.
  • A row with any missing clearance input is counted as Needs review rather than Clear — the queue never assumes a check has passed. On the instance used for this page, QC had not been evaluated for any row, so the Clear lane stayed at zero and Release all clear stayed disabled, including for results that were inside their reference range and carried no chip.
  • The lane tags are computed from the whole queue. Filtering changes the rows you see, not the lane counts.
  • Refer this test produced no visible change when it was clicked on the test instance — no dialog opened and the panel did not change. Treat the button as unconfirmed until your own site has tested it.

Not yet verified

These were not exercised while this page was written, and are not described above as behaviour:

  • Release all clear — the Clear lane could not be populated on the test instance, so the bulk release and its confirmation were never seen.
  • Rows carrying NCE, QC fail, Ack pending or Critical signals. Those filter chips are present and count zero. Modified is the one signal chip that has been seen on a row.
  • Electronic signature on release.
  • By Range of Order Numbers and By Date were opened but not searched against real data.
