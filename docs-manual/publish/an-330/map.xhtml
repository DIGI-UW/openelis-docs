Part of: Set up an analyzer

OpenELIS 3.3.0. In 3.3.0 each analyser keeps its own mapping, and an analyser type's mappings are only the defaults a new analyser starts with. Part 1 describes the 3.3.0 screens, driven on testing on 13 October 2026. Part 2's results screen and Part 3 were captured on 3.2.2.0 and re-checked only where stated. Sites on 3.2.x use Map analyzer codes, resolve held results, and run QC (before 3.3.0).

At a glance

Purpose

Map the codes an analyser sends to OpenELIS tests and result values, clear results that arrived unmapped or undelivered, and monitor quality control.

You'll end up with

Analyser results filing themselves against the right tests, and QC monitored against Westgard rules.

Who does this

A Global Admin for mappings (analyser setup and mappings are Global Admin only in 3.3.0); laboratory staff with results access for held results and QC.

Before you start

The analyser must be set up (see Set up an analyzer). You need to know which OpenELIS test each analyser code corresponds to. That is a clinical decision, not a technical one.

Where

Main menu → Analysers (each analyser's mapping and the undelivered results), Main menu → Analysers → Analyser Types (default mappings), and Main menu → Quality Assurance → Statistical QC.

Mapping and held results are one loop

  1. An analyser sends a code or a result value its mapping does not cover, or a result for an assay that is switched off.

  2. That result is held rather than filed against the wrong test.

  3. You map the code or value on that analyser's mapping, or mark it Do not receive, and apply the mapping.

  4. Matching results from then on flow through normally.

So held results are not a queue of failures. They are how OpenELIS tells you a mapping is incomplete, using real traffic rather than guesswork.

Part 1: Map an analyser's codes

Each analyser has its own mapping

The mapping you set in the setup wizard's Verify step belongs to that analyser. Changing it does not change any other analyser of the same type. The analyser's mapping page, headed type mappings, says so: This analyzer's own mapping. Changes here apply only to this analyzer. They take effect when you confirm the mapping and apply it. It shows Tests mapped, Results mapped and Confirmation, then every analyser code under Test and result mappings.

{{IMG:11-analyser-mapping.png}}

Figure 1. The mapping of one GeneXpert, with HIVVL mapped to HIV Viral Load and its call result going to the HIVVIRALLOAD component.

An expanded code shows the Analyser code, its LOINC, the OpenELIS test it files against, the component a record lands on (when the test has several), Do not receive, and the coded result values to map for that test. Edited codes carry an Edited tag until the mapping is saved.

To change it:

  1. Open the analyser's setup (row Actions → Edit setup) and go to Verify, or open the analyser's mapping page.

  2. Map or exclude the codes, then select Save mapping and confirm the list in Review changes before saving.

  3. Select Confirm mappings and control recognition. Saving without confirming leaves the confirmation Stale.

  4. On the mapping page, Apply mappings and retry held results applies the confirmed mapping and sends this analyser's held results through it again.

Do not receive is a decision, not a way of postponing. A value the laboratory does not want filed should be excluded deliberately; that is what stops it being held again.

Default mappings on the analyser type

On Analyser Types, a row's View default mappings opens the type's mapping page with the panel Defaults for new analyzers: This is what a new analyzer of this type would start with, matched by standard codes against the current catalog. Nothing here is saved; each analyzer keeps its own mapping. It lists the analysers using the type. To give a group of instruments different defaults, use Duplicate Profile.

{{IMG:12-type-defaults.png}}

Figure 2. Default mappings for the GeneXpert type. Its counts (1 of 31 tests) differ from the analyser's own mapping in Figure 1 (3 of 31).

Control result recognition

Each mapping carries Control result recognition: the rules that identify quality-control material so it is not treated as a patient result. For the GeneXpert type the rule is Order field 12 equals Q. Confirming the mapping confirms these rules too.

Part 2: Review held results

From the Analyzers list, a banner appears when an analyzer has held results:

type has held results. Map unknown tests or result values before using these results clinically. Review held results

The screens in this part were captured on 3.2.2.0. That opens the analyzer's results screen, headed Analyzer: type, with a lab number search.

Held results. The first row is ordinary and carries Save, Retest and Ignore; the two Held rows carry none.

What the screen tells you

  • "n analyzer results need attention"

  • "Held results cannot be accepted. Resolve the Analyzer Type mapping so the next matching result can enter the normal review workflow."

  • "n QC controls hidden from patient view"

  • A legend for the flag marking a nonconforming sample or order, or a rejected test

Columns are Sample Info, Test Name, Result, Test Date, then Save, Retest, Ignore and Notes. Bulk actions across the top: Save All Results, Retest All Tests, Ignore All Results.

Two reasons a result is held

Held row shows

Meaning

An analyzer code with no OpenELIS test, e.g. UNMAPPED-MTB

The instrument sent a test code the type has no mapping for

A known code with an unmapped value, e.g. MTB-RIF → REVIEW REQUIRED

The test is mapped but this particular result value is not

Held rows display the analyzer code explicitly, and the second kind carries a Review Analyzer Type mapping link straight to the editor.

panel_c1

A held row has no Save, Retest or Ignore checkboxes at all. Ordinary rows have all three; held rows have none, and the bulk actions do not reach them. So a held result cannot be accepted, retested or ignored. It is inert until the mapping is resolved.

That is the point of the hold: there is no way to push through a result whose meaning OpenELIS does not know.

How to clear them

  1. Open the analyser's mapping (row Actions → Edit setup → Verify, or the Review Analyzer Type mapping link on a held row).

  2. Map the unmapped code or value, or mark it Do not receive. Save and confirm the mapping.

  3. Select Apply mappings and retry held results on the analyser's mapping page. In 3.3.0 this sends the analyser's held results through the new mapping (OGC-1220). It was not exercised for this page.

QC controls

A collapsible QC Controls (n) section at the foot lists results the control-recognition rules identified as quality-control material. It shows Sample Info, Test Name and Result, read-only, with no Save, Retest or Ignore.

These are deliberately hidden from patient view. Their presence here is the visible outcome of the control-recognition rules in Part 1: if genuine patient results appear in this section, the rules are too broad, and if control material appears in the main table, they are too narrow.

On the reference instance the QC control carried a lab number in a distinct series (DEV012698…) from the patient results (DEV012610…).

Undelivered analyser results

The Analysers list shows a banner when the Bridge is holding results it could not deliver to OpenELIS, for example 35 analyzer results were not delivered. Review undelivered results opens Analyser import issues. Its Undelivered analyzer results table lists each result with the analyser (or Unrecognized sender and its address), when it was received, its status, the reason and details. Held results are still reviewed in each analyser's own results worklist.

{{IMG:13-undelivered.png}}

Figure 3. Undelivered analyser results. The first row was retried after the GeneXpert was set up.

Retry sends a result again once its cause is fixed; Dismiss hides it and keeps it in the Bridge for audit. The usual cause is The sender matches no saved analyzer connection. Set up the analyzer, then retry. On testing, a result retried after a GeneXpert connection was activated stayed undelivered, and its details changed from No active analyzer connection listens on port 12001 to FHIR routing requires control-result recognition from a pinned profile.

Part 3: Westgard quality control

Main menu → Quality Assurance → Statistical QC holds these screens in 3.3.0 (in 3.2.2.0 they were under Main menu → Analyzers → Quality Control). For the daily review, see Statistical QC: overview and daily review.

panel_c1

Control recognition and Westgard rules are different things. Recognition (Part 1) decides what counts as a control. Westgard rules decide whether the controls are passing. A lab can have recognition right and QC failing, or the reverse.

QC Dashboard

/qa/qc/dashboard: "Monitor instrument QC status and alerts", with a last-updated time and a Refresh.

Tiles: Instruments In Control, Warning Status and Out of Control (each as a count and a percentage of total instruments), plus % Instruments In Control (labelled Overall QC Pass Rate in 3.2.2.0).

The QC Dashboard, Instruments tab.

Instruments tab

Columns: Instrument Name, Type (the profile slug), Location (the lab unit), Status, Analytes, Recent Violations, Last Update, and a View action. Analytes appear with a sigma value, e.g. HIV Viral Load(Serum) 0.0σ.

Alerts tab

QC Violations & Alerts, filtered by Time Period (e.g. Last 72 Hours), split into:

  • Active QC Violations: "n unacknowledged violation(s) requiring attention"

  • Acknowledged Violations: "n violation(s) have been acknowledged"

So violations carry an acknowledgement state: a violation stays active until someone acknowledges it, which is what stops it being silently overlooked.

Per-instrument QC detail

/analyzers/qc/instruments/<id>, reached from View. Headed with the instrument name, profile slug, lab unit and status, then a card per analyte showing its z score and the last result time.

Two tabs: Activity Timeline (alerts and corrective actions for the period) and Control Chart.

The control chart: standard deviations against time, with the mean and the ±1σ, ±2σ and ±3σ limits.

The chart is a Levey-Jennings plot, the standard way to see a shift or trend that individual results do not reveal. Chart tools allow a table view and full-screen.

Rule Configuration

/qa/qc/rule-config: "Configure Westgard rules per analyzer and test combination".

Configured Rule Sets lists Analyzer, Test and Enabled Rules as a ratio, e.g. 4/8. Rules are set per analyzer and test pair, so one instrument can apply different rules to different analytes. The row Actions menu offers Edit.

Configured rule sets, one per analyzer and test pair.

Eight rules are available, in two groups. Each enabled rule has a Severity toggle of Warning or Rejection, so the grouping is a default rather than a fixed classification.

Rejection rules

Rule

Fires when

1:3s

One control exceeds ±3SD

2:2s

Two consecutive controls exceed ±2SD in the same direction

R:4s

The range between two controls exceeds 4SD

Warning rules

Rule

Fires when

1:2s

One control exceeds ±2SD

3:1s

Three consecutive controls exceed ±1SD in the same direction

4:1s

Four consecutive controls exceed ±1SD in the same direction

10:x

Ten consecutive controls on the same side of the mean

7:T

Seven consecutive controls trending in the same direction

1:2s is conventionally used as a warning that triggers review rather than rejection, because it fires often by chance. The multi-point rules (10:x, 7:T, 3:1s, 4:1s) detect drift and bias that no single result would reveal.

Control Lots

/qa/qc/control-lots: "Manage QC control lots for Westgard rule evaluation", with a status filter and New Control Lot.

Control lots, with control level, calculation method and expiration date.

Columns: Lot Number, Control Material, Manufacturer, Control Level, Status, Calculation Method and Expiration Date.

Calculation method determines where the mean and standard deviation come from. Manufacturer Fixed uses the values printed on the control insert. The other methods in the list were not exercised for this page. Which is chosen changes what the Westgard rules measure against, so it is not a cosmetic field.

Lots carry expiration dates. An expired lot is worth checking when QC evaluation stops behaving as expected.

Tips

  • Mappings belong to each analyser. Change one instrument without affecting the others; change a type's defaults only for analysers set up later.

  • Save and confirm. Saving alone leaves the confirmation Stale.

  • Do not receive is a deliberate answer. Use it rather than leaving a value unmapped.

  • Switch off assays an instrument does not run, in the setup wizard's Assays step. A result for an assay that is off is held, not lost.

  • Check the QC Controls section as a sanity check on the control-recognition rules, in both directions.

  • Westgard rules are set per analyser and test, so enabling a rule for one analyte does not enable it for the others.

  • Violations stay Active until acknowledged.
