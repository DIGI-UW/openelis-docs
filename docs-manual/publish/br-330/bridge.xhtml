Reference · Lab IT and system administrators

Updated for certificate pairing. From Analyzer Bridge 3.2.7 and OpenELIS 3.3.0, OpenELIS and the Bridge trust each other by certificate, not by password. They pair once with a one-time code, either configured on both sides or entered by a Global Admin on the Analysers page. This page was rewritten on 13 October 2026 for Bridge 3.4.1 and OpenELIS 3.3.0-SNAPSHOT. An OpenELIS that still connects with a Bridge password (3.2.x) needs the password procedure in Install the Analyzer Bridge (before 3.3.0).

At a glance

Purpose

Install and configure the Analyzer Bridge, pair it with OpenELIS, and confirm that analyzer types load in OpenELIS and that results can be delivered.

You'll end up with

A running Bridge, and an OpenELIS whose Analysers page says Paired with the Analyzer Bridge and whose Analyser Types list is filled from the Bridge.

Who does this

Lab IT or whoever runs the OpenELIS server installs the Bridge. Pairing on the Analysers page needs a Global Admin: from 3.3.0, analyzer setup, types, mappings and pairing are Global Admin only.

Before you start

A host with Docker (amd64 or arm64), the OpenELIS base URL, and the analyzers you intend to connect. A TLS keystore is optional: the Bridge generates its own certificate if you do not supply one.

Where

The Bridge host's shell and the OpenELIS server configuration, then Main menu → Analysers in OpenELIS to check or enter the pairing.

What the Bridge is responsible for

The Bridge and OpenELIS split the work along a deliberate line, and most configuration mistakes come from putting something on the wrong side of it.

The Bridge owns

Analyzer profiles, durable analyzer connections, the listeners themselves, message parsing, control-result recognition, file watching, and delivery of one normalised result to OpenELIS.

OpenELIS owns

The lab-facing setup workflow, references to Bridge connections, lab units, local test catalogue bindings, verification and audit, activation intent, quality control, held results, and review.

A profile describes how one analyzer type communicates, and supplies the defaults used when a new connection of that type is created. A connection is one durable, saved instrument: it pins a profile revision and owns its own source binding. Every normalised result the Bridge delivers carries its connection ID, and OpenELIS looks the analyzer up by that ID rather than inferring identity from the analyzer's name.

Protocol versus transport

These are configured separately and are easy to conflate. Protocol is the shape of the message; transport is how it arrives.

Protocol

ASTM, HL7, CSV: the message format and syntax.

Transport

TCP, MLLP, Serial, File, HTTP: how the message reaches the Bridge.

An HL7 connection over MLLP and an ASTM connection over TCP are both "a socket on a port", but they parse nothing alike, and the profile is what decides the parsing. One combination is rejected: HL7 in TCP client mode for inbound results is not supported. Inbound HL7 must be a server connection that the analyzer connects to.

The port map

The Bridge binds a small set of shared listeners at startup, before any analyzer is configured. Saved ASTM and HL7 connections receive through these shared ports rather than each opening its own.

FILE connections need a mounted directory, not a port. The directory must lie under bridge.file.import-roots (default /data/analyzer-imports and /data/analyzer-drops).

A published port answering does not mean anything is listening. Docker's port forwarder accepts connections on a published host port whether or not the container has bound it, so a successful telnet or nc proves nothing. Check inside the container with docker exec <container> netstat -ltn, or read the health endpoint.

Step 1: Get the image

bash

From Bridge 3.3.1 the image is published for both amd64 and arm64, so it runs natively on Apple Silicon and ARM servers. Pin a version tag in production rather than latest, so an upgrade is a decision. The repository's docker-compose.yml runs the published image; it does not build from the checkout.

The image itechuw/astm-http-bridge is still published as a legacy alias from the repository's previous name. New installations should use itechuw/openelis-analyzer-bridge.

Step 2: TLS: let the Bridge generate its certificate, or supply your own

The image runs the prod profile by default. On first start, if no keystore is supplied, the Bridge generates its own key pair and serves HTTPS with it. The key pair and the pairing record live under /data/openelis-analyzer-bridge/identity/, so keep /data/openelis-analyzer-bridge on a persistent volume. If that volume is lost, the Bridge presents a new certificate and has to be paired again.

If your site requires its own certificate, supply a PKCS12 keystore; it is used as given:

yaml- -Dserver.ssl.keyStoreType=PKCS12 -Dserver.ssl.keyStorePath=/app/bridge-keystore.p12 -Dserver.ssl.keyStorePassword=CHANGE_ME volumes: - ./bridge-keystore.p12:/app/bridge-keystore.p12:ro]]>

To select a different Spring profile, set SPRING_PROFILES_ACTIVE. The older SPRING_PROFILE still works when it is the only one set, and logs a warning.

Step 3: Pair OpenELIS with the Bridge

Pairing replaces passwords between OpenELIS and the Bridge. Each side keeps its own key pair; while pairing, each records the other's certificate fingerprint, and from then on accepts only that certificate in both directions. OpenELIS calls the Bridge presenting its certificate and sends no password; the Bridge delivers results to OpenELIS presenting its certificate, and OpenELIS refuses a password or session on the delivery path.

The Bridge accepts one pairing code, once. There are two ways to give OpenELIS that code.

Option A: configure the same code on both sides (recommended for Compose stacks)

  1. Choose a code and give it to the Bridge as BRIDGE_PAIRING_CODE, and to OpenELIS as ANALYZER_BRIDGE_PAIRING_CODE (property analyzer.bridge.pairing-code):

    yaml

  2. Start both. OpenELIS pairs on startup, or on its first call to the Bridge if it is still unpaired. No one has to enter anything.

  3. If the Bridge refuses a configured code (wrong, or already used), OpenELIS does not try it again, so the Bridge keeps its attempts for a code entered on the page.

Option B: enter the code on the Analysers page

  1. Start the Bridge without BRIDGE_PAIRING_CODE. An unpaired Bridge logs a new code at each start:

    text

    Read it with docker logs openelis-analyzer-bridge. Because a new code is generated at every start, use the code from the most recent start.

  2. Sign in to OpenELIS as a Global Admin and open Main menu → Analysers. An unpaired OpenELIS shows The Analyzer Bridge is not paired, with a Pairing code field. Results the Bridge receives before pairing wait in the Bridge and are delivered once it is paired.

  3. Enter the code and select Pair. Pair stays disabled until a code is typed.

  4. When pairing succeeds, the page shows Paired with the Analyzer Bridge, with the Bridge address, the start of the Bridge certificate's fingerprint and when it paired.

Pairing again

A paired Bridge refuses its current code. To pair again, for example after reinstalling either side or losing the Bridge's /data volume, configure a new BRIDGE_PAIRING_CODE on the Bridge, restart it, then select Pair again on the Analysers page and enter the new code (or set it as OpenELIS's configured code). OpenELIS applies a new pairing at once, without a restart. Cancel closes the field without changing the pairing.

{{IMG:02-pair-again.png}}

Figure 2. Pair again opens the Pairing code field. Pair is disabled until a code is entered.

Passwords before pairing

A Bridge with BRIDGE_AUTH_PASSWORD set still accepts that password until it is first paired, so an older OpenELIS that uses a password is not cut off by a Bridge upgrade. The first pairing ends password access. For an OpenELIS 3.3.0 site, leave the password empty: the Bridge then logs No bridge.security.password is set: only the paired OpenELIS certificate authenticates. The shipped default changeme stops the Bridge at startup outside the dev and test profiles.

Step 4: Configure Bridge → OpenELIS (where results go)

This is the direction results travel. Set org.itech.ahb.forward-http-server.uri to the OpenELIS base URL. From Bridge 3.3.1 the Bridge derives both paths from it: results are posted to {uri}/analyzer/fhir, and forwarding health reads {uri}/health.

yaml

In Docker the same value can be given as ORG_ITECH_AHB_FORWARD_HTTP_SERVER_URI. The configuration file, if you use one, is read from /app/configuration.yml. If that file is absent the Bridge starts on its built-in defaults and logs Properties location [file:/app/configuration.yml] not resolvable.

Once paired, the Bridge presents its own certificate on every delivery, so the forwarding username and password are not needed (they are sent only before pairing, and OpenELIS 3.3.0 refuses them on the delivery path). The Bridge must also trust OpenELIS's HTTPS certificate: it takes the fingerprint OpenELIS sends while pairing, or a trust store that validates OpenELIS's certificate. The OpenELIS Compose stack gives the Bridge the stack's trust store, so OpenELIS stays trusted after its certificate is regenerated.

Results are not lost while OpenELIS is down. Every received result is written to a durable outbox before any network call and retried (by default up to 150 attempts with backoff, sized for an overnight outage) until OpenELIS accepts it or it lands in the dead-message queue with its payload intact. Keep bridge.outbox.db-path on the persistent volume: between receipt and delivery, that file is the only copy of the result. Results the Bridge cannot deliver show in OpenELIS as a banner on the Analysers page, n analyzer results were not delivered, with Review undelivered results (see Map analyzer codes, resolve held results, and run QC).

Step 5: Configure OpenELIS → Bridge

OpenELIS reads the Bridge's profile catalogue, connections and undelivered results over the Bridge's management API. Without a Bridge address, the Analyser Types list is empty and Add Analyser cannot be completed.

Property (environment variable)

Value

analyzer.bridge.url (ANALYZER_BRIDGE_URL)

The Bridge's HTTPS address, with no trailing path, for example https://bridge.openelis.org:8443. Use https://: a plain HTTP request to the Bridge is answered with 400.

analyzer.bridge.pairing-code (ANALYZER_BRIDGE_PAIRING_CODE)

Optional. The Bridge's configured pairing code, for Option A in Step 3. Leave it empty to pair on the Analysers page.

OpenELIS 3.3.0 no longer uses analyzer.bridge.username or analyzer.bridge.password. It creates its own key pair the first time it pairs and keeps it in its database, with the private key encrypted, separate from the certificate it serves HTTPS with, so renewing that certificate does not break the pairing.

Installer-based sites. To receive results from a paired Bridge, OpenELIS's HTTPS connector must request (not require) client certificates. The OpenELIS Docker images do this. The Linux installer's oe_server.xml template did not yet do so when OpenELIS-Global-2 #4657 merged, so an installer-based site cannot receive deliveries from a paired Bridge until its server.xml is updated.

Step 6: Confirm the pairing and the catalogue

  1. Open Main menu → Analysers. The page should say Paired with the Analyzer Bridge (Figure 1).

  2. Open Analysers → Analyser Types. The list is filled from the Bridge's profiles, each marked Shipped or Site-created with its revision.

  3. On the Bridge, anonymous callers can reach only the overall health, GET /pairing, POST /pairing and the analyzer transport POST /input; everything else answers 401. GET /pairing is a quick check of the Bridge side:

    bash

Step 7: Check health

Anonymously, /actuator/health returns only the overall status. The overall status includes forwarding to OpenELIS, so a Bridge whose forward URI is unset or unreachable reports {"status":"DOWN"} with HTTP 503 even though it is running. Component detail (disk space, file watcher, forwarding, MLLP, outbox, serial) requires the paired OpenELIS certificate; read it from the OpenELIS analyzer pages rather than with a password.

Tips

  • Work through the two directions separately. Forwarding failing shows up as results waiting in the outbox and the results were not delivered banner; the management direction failing shows up as an empty Analyser Types list.

  • Keep /data/openelis-analyzer-bridge across restarts and upgrades. The connection catalogue, profile catalogue, file-processing state, delivery outbox, the generated identity and the pairing record all live there. Losing it means pairing again.

  • Publish only the shared ports you use. If no analyzer will use HL7, leave MLLP_ENABLED off and do not publish 2575.

  • On restart the Bridge restores active connections from their last successfully activated values, so a connection edited but never activated comes back as the older working version.

  • Closing a connection waits up to 30 seconds for deliveries in flight. A failed drain reports failure and keeps ownership; do not treat it as complete.

  • If the outbox database cannot be opened, the Bridge renames it aside, logs the path at ERROR and starts a fresh one so the lab keeps working. Preserve that renamed file and reconcile it against OpenELIS.
