How-to · Lab administrators

Part of: Set up an analyzer

Status: draft, unverified against 3.2.2.0. Captured from analyzers.openelis-global.org on 15 September 2026.

At a glance

Purpose

Map the codes an analyzer sends to OpenELIS tests and result values, clear results that arrived unmapped, and monitor quality control.

You'll end up with

Analyzer results filing themselves against the right tests, and QC monitored against Westgard rules.

Who does this

Lab administrators. Access is set by user permissions and can be configured by your administrator.

Before you start

The analyzer must exist and its type must be known. You need to know which OpenELIS test each analyzer code corresponds to — a clinical decision, not a technical one.

Where

Main menu → Analyzers → Analyzer Types, and Main menu → Analyzers → Quality Control

Mapping and held results are one loop

These two tasks look separate and are not:

  1. An analyzer sends a code or a result value OpenELIS has no mapping for.

  2. That result is held rather than filed against the wrong test.

  3. Holding it adds the unknown value to the analyzer type's mapping list, badged Observed in held results.

  4. You map it.

  5. Matching results from then on flow through normally.

So held results are not a queue of failures — they are how the system tells you the mapping is incomplete, using real traffic rather than guesswork. A type can look fully mapped until an instrument sends something new.

Part 1 — Edit an analyzer type's mappings

Main menu → Analyzers → Analyzer Types → row Actions (⋮) → Edit mappings.

The row Actions menu also offers Duplicate Profile, View history and Deactivate.

Changes are shared, and staged

The editor opens on a warning worth reading twice:

Shared Analyzer Type mappings. Changes create a new mapping candidate for n analyzers using this type. Existing active configurations do not move until the candidate is confirmed and adopted.

The mapping editor: the shared-type warning, the analyzers using this type each badged Update available, the mapping counts, and the analyzer codes.

Two consequences:

  • You are editing every analyzer that shares this type, not one instrument. The editor lists them under Analyzers using this type, each badged Update available where a newer candidate exists that the analyzer has not yet taken up.

  • Changes do not take effect immediately. They form a candidate. Active configurations keep running on what they have until the candidate is confirmed and adopted. So editing mappings will not silently change how a running analyzer behaves mid-shift.

If only one instrument should behave differently, Duplicate Profile instead — that creates a Site-created type recorded as derived from the revision it came from, leaving the shared type alone.

The result count grows as unmapped values are discovered in held results, so a type can gain a result value without anyone changing anything.

The Results mapped ratio here and the one on the Analyzer Types list can disagree — a type reading 11/17 in this editor showed 10/16 on the list. Treat the editor as authoritative when working on mappings.

Mapping a code

Each analyzer code is listed with a status and expands to show its detail. The guidance is explicit: review each analyzer code independently, and either map it to an active OpenELIS Test or explicitly exclude it.

An expanded code shows:

  • Analyzer code — what the instrument sends, e.g. MTB-RIF

  • LOINC — e.g. 85362-2

  • OpenELIS test for code — the test to file against, e.g. Results - Xpert MTB/RIF

  • Do not receive code — explicitly exclude it

Then, beneath, every result value that code can send, each with its own OpenELIS result for value selector and its own Do not receive option. For the GeneXpert MTB-RIF code those were MTB DETECTED, NOT DETECTED, HIGH, MEDIUM, LOW, VERY LOW, INDETERMINATE, ERROR, NO RESULT and REVIEW REQUIRED.

"Do not receive" is a real answer, not a way of postponing. A value the laboratory does not want filed should be excluded deliberately — that is what stops it being held again. The list view shows how many are so marked, e.g. 6 marked Do not receive.

A value discovered through a held result carries the badge Observed in held results and sits unmapped with Choose an OpenELIS result. Those are the ones to work through.

Control result recognition

The same editor carries Control result recognition — the rules that identify quality-control material so it is not treated as a patient result.

Recognition is rule-based, and the rules are shown. Observed examples:

  • On the shipped GeneXpert ASTM type: Order field 12 equals Q

  • On the shipped Bruker FluoroCycler type: control task equals Positive, Negative or Standard, and specimen ID starting C+ or C-

Getting this wrong is a patient-safety matter in both directions. Too narrow, and control material is filed as a patient result. Too broad, and genuine patient results are hidden from patient view as controls.

Saving

  1. Update shared mappings — saves the candidate. The page reports Mappings saved and the Confirmation flips to Stale.

  2. Confirm mappings and control recognition — confirms it, so analyzers can adopt it. Confirmation returns to Current, stamped with who confirmed and when.

Both steps are needed. Saving alone leaves the confirmation stale and the candidate unadopted.

Part 2 — Review held results

From the Analyzers list, a banner appears when an analyzer has held results:

type has held results. Map unknown tests or result values before using these results clinically. Review held results

That opens the analyzer's results screen, headed Analyzer: type, with a lab number search.

Held results. The first row is ordinary and carries Save, Retest and Ignore; the two Held rows carry none.

What the screen tells you

  • "n analyzer results need attention"

  • "Held results cannot be accepted. Resolve the Analyzer Type mapping so the next matching result can enter the normal review workflow."

  • "n QC controls hidden from patient view"

  • A legend for the flag marking a nonconforming sample or order, or a rejected test

Columns are Sample Info, Test Name, Result, Test Date, then Save, Retest, Ignore and Notes. Bulk actions across the top: Save All Results, Retest All Tests, Ignore All Results.

Two reasons a result is held

Held row shows

Meaning

An analyzer code with no OpenELIS test, e.g. UNMAPPED-MTB

The instrument sent a test code the type has no mapping for

A known code with an unmapped value, e.g. MTB-RIF → REVIEW REQUIRED

The test is mapped but this particular result value is not

Held rows display the analyzer code explicitly, and the second kind carries a Review Analyzer Type mapping link straight to the editor.

panel_c1

A held row has no Save, Retest or Ignore checkboxes at all. Ordinary rows have all three; held rows have none, and the bulk actions do not reach them. So a held result cannot be accepted, retested or ignored — it is inert until the mapping is resolved.

That is the point of the hold: there is no way to push through a result whose meaning OpenELIS does not know.

How to clear them

  1. Open Review Analyzer Type mapping, or go to the type's Edit mappings.

  2. Map the unmapped code or value, or mark it Do not receive.

  3. Save and confirm the mappings.

panel_c1

Known defect — already-held results are not released. Tested on 15 September 2026: mapping a held value (REVIEW REQUIRED → INDETERMINATE), saving and confirming left the held row exactly as it was — still Held, still counted as needing attention, still with no actions available.

Since held rows also cannot be actioned manually, a result that is already held currently has no resolution path. The banner wording ("so the next matching result can…") is literal. Fixing the mapping prevents recurrence; it does not clear the backlog.

Tracked as OGC-1220, with re-evaluation on confirmation as the agreed fix. Until then, expect the attention count to stay above zero on any analyzer that ran before its mappings were complete.

QC controls

A collapsible QC Controls (n) section at the foot lists results the control-recognition rules identified as quality-control material. It shows Sample Info, Test Name and Result, read-only — no Save, Retest or Ignore.

These are deliberately hidden from patient view. Their presence here is the visible outcome of the control-recognition rules in Part 1: if genuine patient results appear in this section, the rules are too broad, and if control material appears in the main table, they are too narrow.

On the reference instance the QC control carried a lab number in a distinct series (DEV012698…) from the patient results (DEV012610…).

Part 3 — Westgard quality control

Main menu → Analyzers → Quality Control holds three screens.

panel_c1

Control recognition and Westgard rules are different things. Recognition (Part 1) decides what counts as a control. Westgard rules decide whether the controls are passing. A lab can have recognition right and QC failing, or the reverse.

QC Dashboard

/qa/qc/dashboard — "Monitor instrument QC status and alerts", with a last-updated time and a Refresh.

Tiles: Instruments In Control, Warning Status and Out of Control (each as a count and a percentage of total instruments), plus Overall QC Pass Rate.

The QC Dashboard, Instruments tab.

Instruments tab

Columns: Instrument Name, Type (the profile slug), Location (the lab unit), Status, Analytes, Recent Violations, Last Update, and a View action. Analytes appear with a sigma value, e.g. HIV Viral Load(Serum) 0.0σ.

Alerts tab

QC Violations & Alerts, filtered by Time Period (e.g. Last 72 Hours), split into:

  • Active QC Violations — "n unacknowledged violation(s) requiring attention"

  • Acknowledged Violations — "n violation(s) have been acknowledged"

So violations carry an acknowledgement state: a violation stays active until someone acknowledges it, which is what stops it being silently overlooked.

Per-instrument QC detail

/analyzers/qc/instruments/<id>, reached from View. Headed with the instrument name, profile slug, lab unit and status, then a card per analyte showing its z score and the last result time.

Two tabs: Activity Timeline (alerts and corrective actions for the period) and Control Chart.

The control chart: standard deviations against time, with the mean and the ±1σ, ±2σ and ±3σ limits.

The chart is a Levey-Jennings plot — the standard way to see a shift or trend that individual results do not reveal. Chart tools allow a table view and full-screen.

Rule Configuration

/qa/qc/rule-config — "Configure Westgard rules per analyzer and test combination".

Configured Rule Sets lists Analyzer, Test and Enabled Rules as a ratio, e.g. 4/8. Rules are set per analyzer and test pair, so one instrument can apply different rules to different analytes. The row Actions menu offers Edit.

Configured rule sets, one per analyzer and test pair.

Eight rules are available, in two groups. Each enabled rule has a Severity toggle of Warning or Rejection, so the grouping is a default rather than a fixed classification.

Rejection rules

Rule

Fires when

1:3s

One control exceeds ±3SD

2:2s

Two consecutive controls exceed ±2SD in the same direction

R:4s

The range between two controls exceeds 4SD

Warning rules

Rule

Fires when

1:2s

One control exceeds ±2SD

3:1s

Three consecutive controls exceed ±1SD in the same direction

4:1s

Four consecutive controls exceed ±1SD in the same direction

10:x

Ten consecutive controls on the same side of the mean

7:T

Seven consecutive controls trending in the same direction

1:2s is conventionally used as a warning that triggers review rather than rejection — it fires often by chance. The multi-point rules (10:x, 7:T, 3:1s, 4:1s) detect drift and bias that no single result would reveal.

Control Lots

/qa/qc/control-lots — "Manage QC control lots for Westgard rule evaluation", with a status filter and New Control Lot.

Control lots, with control level, calculation method and expiration date.

Columns: Lot Number, Control Material, Manufacturer, Control Level, Status, Calculation Method and Expiration Date.

Calculation method determines where the mean and standard deviation come from. Manufacturer Fixed uses the values printed on the control insert; the presence of a named method implies at least one alternative, presumably derived from the laboratory's own cumulative data. Which is chosen changes what the Westgard rules measure against, so it is not a cosmetic field.

Lots carry expiration dates. An expired lot is worth checking when QC evaluation stops behaving as expected.

Tips

  • Editing mappings affects every analyzer sharing the type. Duplicate the type instead if only one should differ.

  • Save and confirm. Saving alone leaves the confirmation Stale and the candidate unadopted.

  • Do not receive is a deliberate answer. Use it rather than leaving a value unmapped.

  • The result count on a type can rise on its own as new values are observed in held results.

  • Held rows cannot be actioned at all, and are not released by fixing the mapping — see OGC-1220.

  • Check the QC Controls section as a sanity check on the control-recognition rules, in both directions.

  • Westgard rules are set per analyzer and test, so enabling a rule for one analyte does not enable it for the others.

  • A rule's Warning-or-Rejection severity is configurable, so two sites running the same rules can behave differently.

  • Violations stay Active until acknowledged.

Not yet documented

Create New Analyzer Type from scratch, View history on a type, the Instrument not listed? path, creating a control lot with New Control Lot, and the calculation methods other than Manufacturer Fixed.
