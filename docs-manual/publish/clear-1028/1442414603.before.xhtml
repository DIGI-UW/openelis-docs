Part of: Test Catalog Management — workflow overview

At a glance

Purpose

Bootstrap or extend a site's test catalog by editing CSV configuration files that OpenELIS loads on startup, instead of hand-entering every test in the Test Catalog Management admin UI.

You'll end up with

A version-controlled, reproducible test catalog — test sections, sample types, dictionaries, tests, and result bindings — upserted into the database on container restart.

Who does this

Implementers and system administrators setting up or maintaining a deployment. This is a configuration-file and deployment task, not an in-app screen. Access to the config tree and container is set by your infrastructure and can be configured by your administrator.

Before you start

Access to the distro repo's configs/configuration/backend/ tree; the instance ID env var for the site (ORG_OPENELISGLOBAL_CONFIGURATION_INSTANCE_ID); LOINC codes where known (don't guess); and the ability to restart the webapp container.

Where

Configuration files under configs/configuration/backend/ in the distro repo — parsed on webapp container startup, not from an admin screen.

Note: This page documents the CSV bootstrap loader — an implementer path for populating the catalog from text files. It is an alternative to authoring tests by hand in the Test Catalog Management admin UI. For the point-and-click editor, see the companion pages under Test Catalog Management.

A practical guide for implementers setting up a new OpenELIS Global site. It covers the five CSV files that define the test catalog — what each column means, how they reference each other, the load order that must be respected, and the gotchas that tend to bite on first deployment.

1. What the test catalog is

In OpenELIS, a "test" is a reportable observation attached to a sample. Before clinicians can order anything, the system needs to know:

  • which test section (department) the test belongs to — Hematology, Biochemistry, Serology, etc.

  • which sample type(s) the test can be run on — Whole Blood, Serum, Plasma, etc.

  • what the result looks like — a number with units, a pick from a fixed list, free text, a titer, a multiselect.

  • optional metadata — LOINC, unit of measure, sort order, active/orderable flags, and translations for every user-facing label.

You can author all of this by hand in the Test Catalog Management admin UI, but on a new deployment that is painfully slow. The CSV bootstrap loader lets you define the whole catalog as text files in the configuration tree. On container startup, OpenELIS parses the CSVs and upserts the rows into the database — so the catalog is version-controlled and reproducible.

This guide covers only the test-catalog CSVs. It does not cover address hierarchies, roles, locales, questionnaires, or OCL — those have their own loaders.

2. Where the files live

All catalog CSVs sit under configs/configuration/backend/ in the distro repo and are mounted into the container at /var/lib/openelis-global/configuration/backend/ via docker-compose:

wide760

Multi-site: the {instanceId} subfolder

Most folders have a per-instance subfolder. The loader picks which one to use from the env var set on the webapp container:

yamlwide760

That tells OpenELIS to load tests/jakarta/*.csv (and sample-types/jakarta/*.csv, etc.). Change it to bogor and you get the Bogor catalog instead. Files directly under tests/ (no instance subfolder) act as a fallback when no instance-specific file is present.

test-results/ is not instance-scoped in the current distro — a single example-test-results.csv covers every instance. This works because the result-binding logic keys on testName and applies to any matching test across instances.

How the loader picks up changes

On startup OpenELIS computes a SHA-256 of each CSV and compares it to a stored checksum. Unchanged files are skipped. Changed files are re-parsed and upserted: rows that already exist get updated; new rows get inserted. You can safely re-run the container after editing a CSV.

To force a re-load of everything, delete the *-checksums.properties files under the configuration directory.

3. Load order (this is the one that bites people)

The loader runs the five domains in a fixed order. If a downstream CSV references an entity that the upstream CSV didn't create, the row is silently skipped and only a warning shows up in the log.

Practically, this means:

  • Every testSection value used in tests.csv must first appear as a testSectionName in test-sections.csv.

  • Every sampleType value used in tests.csv must first appear as a description in sample-types.csv.

  • Every dictionaryCategory value used in test-results.csv must first appear as a category in a dictionary CSV, and each resultValue with resultType=D/M/C must exist as a dictEntry in that category.

  • Every testName used in test-results.csv must exist in tests.csv (or be a base name whose sample-type-augmented variants exist — see §6.2).

If something doesn't show up in the UI after a restart, the log is the first place to look. Rows that fail validation log a warning with the row number and the missing reference.

Step 2 — confirm the sample type exists. Same check in sample-types/{instance}/example-sample-types.csv for Serum.

6. Concepts worth understanding

6.1 Multi-sample-type tests and the | separator

When a test can run on more than one sample type, list them separated by | in the sampleType column:

wide760

The loader creates one OpenELIS test per sample type and names them by appending the sample type in parentheses: Hemoglobin(Whole Blood) and Hemoglobin(Serum). That naming is how the system keeps them distinct internally — users still see "Hemoglobin" in the UI because the localization columns drive display.

6.2 Base test name vs. augmented test name in test-results.csv

Because multi-sample-type tests get split into TestName(SampleType) variants, you'd expect test-results.csv to list each variant separately. It doesn't — and doesn't have to. When you write:

wide760

the loader applies the rule to every test whose base name is HIV Rapid Test, including HIV Rapid Test(Whole Blood), HIV Rapid Test(Serum), and HIV Rapid Test(Plasma). This keeps test-results.csv small and means you can add a sample type in tests.csv without touching result bindings.

If you genuinely want different result rules for different sample-type variants (rare), use the augmented form: HIV Rapid Test(Whole Blood),D,....

6.3 Comments and blank lines

Lines that start with # (after trimming) are skipped, as are blank lines. Use them liberally to group rows — the example files in this commit are heavily commented and it makes them much easier to review. Inline comments (after a value, on the same line) are not supported.

6.4 Localization

Every localization:xx column you add to a file applies to all rows. The loader reads the header to discover which locales are present, then writes one translation per row. Empty cells fall back to English, and if English itself is empty, the loader uses the internal name field (testName, description, dictEntry). Adding a new locale (e.g. Portuguese) is just adding localization:pt to the header and one cell per row — the loader picks it up automatically.

6.5 LOINC

LOINC codes are optional everywhere. Include them when you know them — downstream systems that consume FHIR exports will thank you — and leave them blank otherwise. Don't invent LOINC codes; a wrong code is worse than no code. Look them up at loinc.org or via OCL. Dictionary entries use LOINC answer codes (e.g. LA6576-8 for Positive) rather than observation codes.

6.6 isActive vs. isOrderable

  • isActive=N hides a test from every dropdown, every report, every admin screen. Use it to retire a test permanently.

  • isOrderable=N keeps the test in the system for reporting but prevents users from ordering it directly. This is how reflex-only tests (auto-created when another test returns a flagged value) are configured.

6.7 Idempotency and updates

The loader is an upsert: on every restart it matches existing rows by natural key (usually name) and either updates or inserts. Safe operations:

  • Add a row — it's created.

  • Edit a row — the existing record is updated in place. The checksum for that CSV changes, so the loader re-processes it.

  • Delete a row — the row is not removed from the database. Deletions must be done through the admin UI or a migration. If you need to retire a test, set isActive=N instead.

  • Rename a row's natural key — the loader treats it as a new row. The old record stays behind, inactive-looking. Avoid renames.

6.8 When multiple instances share the host

In this distro, jakarta and bogor are separate physical sites running separate OpenELIS containers. Each container sets its own ORG_OPENELISGLOBAL_CONFIGURATION_INSTANCE_ID. They share the configs/ folder via git but each picks up its own subfolder. If two sites should have identical catalogs, you can symlink tests/bogor → tests/jakarta — or drop the files directly under tests/ with no subfolder and both instances will fall back to them.

7. Pre-deploy validation checklist

Before you restart the container with a new or edited CSV, walk through this:

  • Every testSection value in tests.csv has a row in test-sections.csv.

  • Every sampleType token (each side of |) in tests.csv has a row in sample-types.csv.

  • Every dictionaryCategory in test-results.csv has at least one matching row in a dictionary CSV.

  • For every D/M/C result row, the resultValue exists as a dictEntry in the named category.

  • For every numeric test (N), unitOfMeasure is populated in tests.csv and significantDigits is set in test-results.csv.

  • Exactly one row per dictionary-based test has isNormal=Y (the "expected" answer, used for abnormal-flag highlighting).

  • No row uses smart quotes — only straight ASCII.

  • No trailing commas on header rows; number of cells per row matches the header exactly.

  • Bahasa / French / Spanish cells aren't accidentally English (happens in find-and-replace passes).

  • LOINC codes, where present, look like real LOINC (numeric with a dash and check digit — 2345-7, not 2345).

A quick sanity check from the command line:

bashwide7601 && !/^#/ {print $2}' tests/jakarta/example-tests.csv | sort -u) \ <(awk -F, 'NR>1 && !/^#/ {print $1}' test-sections/jakarta/example-test-sections.csv | sort -u)]]>

If the second command prints anything, those test sections are missing.

8. Common pitfalls

Test doesn't appear in the order-entry dropdown.
Most common cause: isOrderable is blank or N. Second most common: isActive=N on the test section itself.

Test appears but has no result field.
No entry in test-results.csv for that test. Check the log for "no result configuration found".

Dictionary pick-list is empty even though the dictionary CSV has entries.
The dictionaryCategory in test-results.csv doesn't match the category in the dictionary CSV. String match is exact, case-sensitive, and whitespace-sensitive.

Row silently dropped on restart.
Almost always an unresolved foreign-key reference (unknown test section, sample type, or dictionary entry). Grep the log for the row's name.

Changes not picked up after restart.
The checksum didn't change — probably because your edit was in a file that isn't actually being loaded (e.g. you edited tests/bogor/... but the container is running as jakarta). Double-check ORG_OPENELISGLOBAL_CONFIGURATION_INSTANCE_ID.

Localization cells show the internal name instead of the translation.
The localization:xx cell was left blank. The loader falls back to English, and then to the internal name field. Fill in the cell.

A test you deleted from the CSV still shows up in the UI.
Correct behavior — the loader is upsert-only. Retire with isActive=N instead.

LOINC "looked up" by an LLM turns out to be fake.
Don't trust any LOINC code you didn't verify against loinc.org. This is a known failure mode; a wrong code corrupts downstream FHIR exports.
